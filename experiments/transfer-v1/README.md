# 고정 지시문의 새 사례 전이 실험

이 실험은 **라우팅 사례에서 만들어진 지시문을 바꾸지 않고 다른 운영 메커니즘에 적용할 수 있는가**를 확인한다.
사례 안에서 진단·개발 replay·설정 변경은 허용한다. 지시문·모델 가중치를 수정하는 실험은 아니다.

[실제 실행 결과와 한계](REPORT.md): 세 지시문 모두 새 사례 9/9, 기존 사례 수정 지시문 실행에서는 처리량 하락을 관측했다.

## 사전 고정

- `ancestor.source`: 이전 실행의 원래 지시문.
- `source_revised.source`: 이전 라우팅 개발 기록으로 실제 모델이 만든 수정 지시문. 성능 향상이 입증됐다는 이름을 붙이지 않았다.
- `neutral.source`: 신규 사례 구현 전에 작성한 업무 중립 지시문.

[원래 고정 기록](registration.json)에 세 소스의 해시, 질문, 예산, 평가 seed, 실패 처리 원칙을 남겼다.
새 사례 제작 작업자는 고정된 지시문·이전 결과·라우팅 생성기를 읽지 않았다. 다만 상위 설계자는
기존 사례를 아는 같은 프로젝트의 저작자이므로 **독립 저작팀이나 독립 실제 조직 표본으로 세지 않는다**.

연결 검사에서 `gpt-5.4`가 현재 계정에서 지원되지 않아, 사례 실행 전에
[모델 가용성 변경 기록](registration.available-model.json)을 남겼다.
[최종 실행 기록](registration.execution.json)은 `gpt-5.5`, 독립 세션 동시 실행 상한 2개를 지정한다.
에이전트·seed·호출 제한은 유지했다. 지정 순서는 제출 순서이며 세션 안의 동작은 순차 실행된다.
이 로컬 고정 기록은 외부 기관의 사전 등록이나 변경 불가능한 타임스탬프 인증은 아니다.

## 두 사례

| 항목 | 기존 라우팅 사례 | 새 재고 사례 |
|---|---|---|
| 업무 | 요청을 올바른 처리 큐로 보내기 | 절대 재고 snapshot을 올바른 최신 상태로 반영하기 |
| 핵심 메커니즘 | 문구 규칙·큐 처리량·중복 요청 | 논리 이벤트 식별·revision 순서·절대값/증분·상태 보존 |
| 변경 계층 | 라우팅 설정 | 이벤트 반영 설정 |
| 인계 | 상태를 초기화하는 부하·문구 변화 구간 | 재고를 이어받는 부하 구간, 연결을 재개하며 TEMP metadata를 잃는 재시작 모사 |
| 품질 | 정확한 처리·SLA·오처리·중복·미처리 | 각 checkpoint의 정확한 재고, 오래된 값 쓰기와 중복 쓰기 |

새 사례는 다른 데이터 생성기와 SQLite 거래 엔진을 사용한다. `entity_id`로 중복을 억제하면
정상적인 후속 revision도 누락할 수 있다. 최종 재고가 맞더라도 중간에 오래된 값이나 중복을
썼다면 품질 조건은 미충족이다. 운영자 분은 합성 복구 비용 추정이며 실제 인간 노동 측정이 아니다.

## 실행과 평가

```bash
./bench transfer \
  --registration experiments/transfer-v1/registration.execution.json \
  --out runs/new-transfer
```

3개 지시문 × 2개 사례 = 6개 모델 개발 세션을 실행한다. 조건별 에이전트 표본은 **1회**다.
세션당 최대 10 action, 개발 replay 2회, 호출당 120초·출력 131,072바이트를 허용한다.
모든 개발 세션을 마친 뒤 `deployments.freeze.json`에 배포 정책을 고정한다.
그 후에만 고정된 정책을 평가 seed 701·702·703에서 실행한다. 각 평가에는 동일한 workload의
기존 정책 대조가 있다. 평가 seed 3개를 에이전트 반복 3회나 독립 프로젝트 3개로 세지 않는다.

실패·무배포·권한 위반·형식 오류도 결과에 포함한다. 전이의 1차 조건은 새 사례의 모든
checkpoint에서 정확한 재고, 오래된 값/중복 쓰기 0, 배포 후 정상 종료다. 거부된 action은 별도 기록한다.
서로 다른 사례의 지표를 한 점수로 합치거나 표본 1회로 유의확률을 계산하지 않는다.

## 해석 범위

새 사례는 **지시문 작성 이후 만든 다른 합성 메커니즘**이라는 의미의 holdout이다.
모델 사전학습에 재고 처리 알고리즘이 없었다는 뜻은 아니다. 개발/평가 생성기는 서로 다른
namespace와 값을 쓰지만 같은 전송 패턴을 공유한다. 평가 seed는 새로운 메커니즘으로의 추가 전이를 검증하지 않는다.

사례별 policy API도 바뀐다. 따라서 `policy_domain_mismatch`는 지시문/API 이식성의 실패로
해석하며 일반 지능 부족으로 확대하지 않는다. 업무 중립 지시문은 이 교란을 살펴보는 대조군이다.
고정 모델 이름도 공급자의 불변 내부 스냅샷 인증은 아니다. 공유 호스트에서의 호출 시간은
독립적인 모델 지연시간 측정이 아니며, 악성 에이전트를 격리하는 실험도 아니다.

실제 FDE 조직·인간 비교·독립 사례군 모집·AI 재귀개선 이득·AGI 판정은 이 실험의 주장 범위에 포함하지 않는다.
