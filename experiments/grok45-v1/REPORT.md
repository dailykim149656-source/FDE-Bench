# Grok 4.6: 45세션 반복 실험 결과

**45세션을 실행했고, 19세션이 배포·종료와 사전 정의한 사례 품질 조건을 모두 충족했다. 나머지 26세션은 전부 120초 호출 시간 초과로 끝났다.** 배포된 정책 19개 사이에서는 품질 조건의 실패가 관측되지 않았다. 이번 결과는 과제 자체의 변별력보다 현재 실행 경로의 신뢰성 문제를 보여준다.

## 조건별 결과

각 칸은 **배포·종료 및 해당 사례 조건 충족 세션 / 등록한 5세션**이다. 서로 다른 사례의 조건을 공통 능력 점수로 합산하지 않는다.

| 메커니즘 | 원래 지시문 | 이전 개발 기록 기반 수정 지시문 | 중립 지시문 |
|---|---:|---:|---:|
| Support routing | 2/5 | 0/5 | 0/5 |
| Inventory reconciliation | 3/5 | 4/5 | 4/5 |
| External-effect recovery | 2/5 | 2/5 | 2/5 |

모든 세션은 `xai/grok-4.6` 요청 모델명, 같은 Codex CLI 하네스, 같은 제한으로 실행했다. 각 배포 정책에는 공통 평가 seed 5개를 적용했다. **45개 에이전트 세션, 225개 workload 평가, 저작한 합성 메커니즘 3개, 독립 실제 고객 사례 0개**다. 모델명은 불변 공급자 스냅샷 인증이 아니다.

## 무엇이 실패했는가

26건의 세션 종료 오류는 모두 `timeout: invocation deadline exceeded`였다. 첫 호출에서 17건, 마지막 정상 JSON 응답의 action이 inspect였던 경우 5건, request_approval 2건, configure 1건, replay 1건이었다. 여기서 정상 JSON 응답은 도구가 action을 승인했다는 뜻이 아니다.

정상 JSON으로 파싱됐지만 프로토콜이 거부한 action도 25건 있었다.

- `unexpected_policy_payload`: 22건. configure 이외의 action에 policy를 보냄.
- `unexpected_approval_payload`: 3건. deploy 이외의 action에 approval_id를 보냄.

이 거부를 세션 시간 초과와 중복 없이 합친 '실패 세션 수'로 세지 않는다. 한 세션에 여러 거부가 발생하거나 거부 후 복구할 수 있다. 어느 기록도 모델의 인지적 실패 원인을 직접 증명하지 않는다.

개발 중 정책을 만들었어도 배포하지 못한 세션은 기존 정책으로 평가했다. 따라서 전체 조건 평균의 중복 효과·미처리는 새로 배포된 정책의 오류만을 의미하지 않는다. 실패한 세션을 제외하면 운영 성능을 과대평가하므로 전체 결과를 보존한다.

## 무엇을 확인하지 못했는가

배포된 19개 정책 모두 평가 seed 5개에서 해당 사례의 품질 조건을 충족했다. Inventory의 배포 정책 11개는 동일했고, recovery의 배포 정책 6개도 모두 같은 설정이었다: 상태 조회, 5틱 대기, 없을 때 같은 키로 재시도, 영속 metadata 보존. Support의 두 정책은 소스가 달랐지만 모두 정확한 처리 280건·SLA 내 처리 평균 180건이었다.

따라서 **배포 이후의 과제 해결 품질로 지시문을 구분하는 데에는 실패했다.** 완료율 차이는 관측했지만, 시간 초과와 공급자·프록시·CLI 비용을 분리하지 못했으므로 이를 일반적인 FDE 능력 순위나 지시문 개선의 확정적 효과로 해석할 수 없다. 신규 recovery 사례는 제한된 설정 공간에서 하나의 안전한 정책이 모든 endpoint 변형에 통하는 구조라는 한계도 있다.

이번 실험은 기존 지시문을 재사용한 고정 모델 비교다. 모델 발전의 통제된 비교, Grok의 자기 지시문 개선, 다세대 재귀개선, 인간 대체, AGI를 검증하지 않았다. 이전 GPT 계열 파일럿과는 평가기·호출 경로·표본 설계가 달라 직접적인 모델 우열 비교가 아니다.

## 실행 조건과 연결 문제

세션당 10 action·개발 replay 2회, 호출당 120초·출력 131,072바이트 제한을 적용했다. 모든 세션을 끝내고 정책을 고정한 후에만 최종 평가를 실행했다. 최종 결과를 보고 지시문을 고치거나 실패 세션을 교체하지 않았다.

원래 동시 실행 상한은 3개였다. 사례 데이터 없는 동시 연결 검사에서 3건 모두 시간 초과가 났고 프록시 health 확인도 실패했다. `opencodex ensure` 후 동시 2건은 74.3초·80.5초에 성공했다. **실제 사례 실행 전에 상한만 2개로 낮추는 변경 기록**을 남겼다. 동시성이 원인이었다고 확정한 것은 아니다. 실행 중 별도 health 확인도 3초 내 응답하지 않았으며, 그 후 프록시를 재시작하거나 실험 제한을 변경하지 않았다.

실제 모델 실행과 최종 평가에는 약 110분이 걸렸다. CLI 호출은 163회였고 137회에서 스키마에 맞는 응답을 받았다. 해당 응답에서 보고된 입력 토큰은 4,059,238개, 출력 토큰은 27,062개다. 시간 초과 호출의 사용량은 없어 **전체 사용량·비용이 아니다**. 구현 작업과 연결 검사도 이 합계에서 제외된다. 공급자 내부 모델 호출 수와 순수 추론 지연시간은 확정하지 않았다.
