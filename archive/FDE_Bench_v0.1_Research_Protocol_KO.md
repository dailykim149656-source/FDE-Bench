# FDE-Bench v0.1 — 연구·측정 프로토콜

작성 기준일: 2026-09-07
상태: 연구 설계 제안. 환경 구현, 인간 실험, 모델 평가 및 타당도 검증은 아직 수행하지 않았다.

## 0. 핵심 연구 질문과 주장 범위

낯선 고객 환경에 투입된 AI 시스템이 동일한 권한·업무 자원 제약 아래 도메인을 학습하고, 가치 있는 개입을 선택하고, 구현·배포·채택·인수인계를 거쳐 지속 가능한 순성과를 만들어내는가?

측정 대상은 모델 단독이 아니라 모델, 프롬프트, 메모리, 도구, 실행 프레임워크를 포함한 제출 시스템이다. 모델 비교를 하려면 공통 프레임워크 트랙을 별도로 둔다. FDE라는 직업 전체를 대표한다는 주장은 직무 분석과 현장 전이 실험으로 별도로 검증한다. 핵심 기여 후보는 문제 발견 알고리즘이 아니라 고객 배치 프로젝트 전체를 평가 단위로 만드는 것과 그 측정 프로토콜이다. 최초성은 별도 선행연구 검토 대상이다.

공식 FDE 직무의 탐색, 범위 설정, 구축, 운영 배포, 채택, 현장 피드백 책임을 내용 설계의 출발점으로 사용하되, 채용 공고 한 개를 직무의 전체 정의로 사용하지 않는다.[1]

## 1. 평가 단위: 독립적인 고객 배치 프로젝트

하나의 에피소드는 고객 환경 진입부터 운영 인수인계 및 사후 운영까지 이어진다. 문서 읽기, 코딩, 승인 요청 등을 별개의 문제로 쪼개 평균내지 않는다.

초기 임무 예시:

> 고객사의 업무와 시스템을 조사하고, 주어진 권한·예산·기간 안에서 고객에게 검증 가능한 순가치를 만들어라. 해결 과제와 구현 방식은 사전에 정해져 있지 않다. 고객의 목표·우선순위·위험 허용 범위를 확인하고, 필요한 승인을 받아라. 변경하지 않는 것이 최선이면 근거와 운영 인계안을 남겨라.

알려주지 않는 것: 병목, 근본 원인, 최적 해결책, 조사 순서.
알려주거나 합리적인 비용으로 알아낼 수 있게 하는 것: 권한, 안전 경계, 예산, 고객 가치 기준, 승인 구조, 관련 사실.

‘문제가 미정’인 것과 ‘채점자의 가치 기준을 알아낼 수 없는 것’을 구분한다. 조직의 가치 기준은 환경 생성 때 고정하고 적절한 이해관계자나 문서를 통해 확인 가능해야 한다. 에이전트가 쉬운 KPI를 선언하여 채점 기준을 바꿀 수 없게 한다.

절차는 반복·병렬·우회가 가능하다. 모든 사례에서 새 코드를 만들거나 특정 문서를 작성해야 점수를 받는 방식은 쓰지 않는다. 기존 기능 활용, 프로세스 변경, 제한된 시범 운영, 정당한 무개입도 유효한 해결 방식이다.

## 2. 환경의 수학적 객체

각 프로젝트를 다음 객체로 정의한다.

E_j = (S, A, O, T_j, Z_j, U_j, C_j, B_j, G_j, H_j)

- S: 기술, 데이터, 업무, 조직, 권한, 채택 상태.
- A: 조사, 질의, 실험, 코드·설정 작성, 배포, 승인 요청, 교육, 모니터링 등 허용 행동.
- O: 관측 가능한 문서, 데이터, 로그, 대화와 업무 결과.
- T_j: 상태전이 규칙. 외생 충격과 조직 반응을 포함한다.
- Z_j: 관측 생성 규칙.
- U_j: 운영상의 순가치. 업무 성과, 운영비, 품질·재작업·장애 손실을 포함한다.
- C_j: 개입에 추가로 소요된 비용. FDE 노동, 추론, 도구, 일회성 구축·교육 등.
- B_j: 시간·금전·조직 협업·연산 등 자원 제약.
- G_j: 권한, 안전, 개인정보, 품질 등 비보상적 제약.
- H_j: 개입·인계 후 운영 검증 기간.

조직 구성원의 정책을 고정하면 확장 상태 위의 부분관측 의사결정 문제로 취급한다. 구성원의 정책까지 학습·적응하면 다중 행위자 설정과 그 학습 규칙을 명시한다. 이름을 붙이는 것만으로 현실 타당도가 확보되지는 않는다.

인과 구조를 알고 있는 시뮬레이터 제작자와 제한된 관측만 가진 참가자를 구분한다. 관측으로 구별할 수 없는 두 원인에 대해 서로 다른 ‘정답 원인’을 강요하지 않는다. 원인 이름이나 그래프의 정확 일치는 주 점수가 아니다. 동일한 관측·개입 결과를 설명하는 여러 모델과 여러 해결책을 허용한다.

## 3. 실행 구조

### 3.1 실제 실행되는 기술 계층

버전이 고정된 데이터베이스, 저장소, 웹 서비스, 테스트, 배포 환경을 제공한다. 에이전트가 만든 코드는 실제 실행되며 이후 업무 이벤트가 그 코드를 통과한다. ‘자동화를 배포했다’는 문장이나 deploy=true 플래그로 성과가 발생해서는 안 된다. 프로세스 변경도 실제 라우팅, 승인 경로, 직원 업무량을 바꿔야 한다.

WebArena, OSWorld, TheAgentCompany는 통제된 실제 소프트웨어 환경과 실행 상태 기반 평가의 선례다.[2–4] 여기서는 그 구성을 고객 프로젝트와 운영 결과 수준으로 확장한다.

### 3.2 조직 계층

구성원마다 알고 있는 사실, 목표, 가용 시간, 승인 권한, 업무 부담, 수용 조건을 가진다. 승인과 채택은 설명의 문체가 아니라 검증 가능한 근거·권한·부담·결과와 연결한다. 정책은 하나만 쓰지 않고 실무 사례로 보정한 여러 조직 모델을 사용한다.

코어 트랙에서는 중요한 약속·승인·요청을 명시적 의미 구조로 확정한다. 자유로운 표현을 허용하더라도 실제 상태 변경은 검증된 의미와 증거에 의해 발생한다. 자연어를 구조화하는 파서 자체가 오류원이므로 별도 검증하고, 참가자가 구조화된 내용을 확인할 수 있게 한다. 템플릿 또는 사전 생성한 표현을 버전 고정하여 언어 표현의 변동을 분리한다.

이 구조는 조직 내 조정을 추상화한 것이지 모든 인간관계를 재현한 것은 아니다. 자연어 협상·장기 신뢰·비공식 권력에 대한 강한 주장은 실제 인간 참여 실험 없이는 하지 않는다. SOTOPIA는 사회적 상호작용을 별도의 능력으로 평가하는 참고 연구다.[5]

### 3.3 독립 평가 계층

평가기는 에이전트 컨테이너 밖에서 운영하고 읽기·쓰기 접근을 차단한다. 성과는 독립된 업무 이벤트 원장과 인수검사로 계산한다. 대시보드 숫자 변경, 로그 삭제, 테스트 코드 조작, 승인 위조로 점수가 오르지 않아야 한다. 검증기의 비용은 참가자 비용과 구분한다.

## 4. 재현성의 세 수준

1. 환경 재생: 같은 스냅샷, 외생 이벤트, 정규화된 행동·응답 기록을 재생하면 같은 상태와 점수가 나온다.
2. 에이전트 재실행: 처음부터 다시 판단하게 하면 다른 행동이 나올 수 있다. 이것은 반복 평가할 대상이다.
3. 결론 재현: 독립 실행과 별도 조직 모델에서도 효과와 비교 결론이 지정한 불확실성 범위 안에서 유지되는지 검증한다.

같은 seed만으로 플랫폼·모델 실행까지 완전 결정론적이라고 주장하지 않는다. PyTorch 공식 문서도 버전과 플랫폼을 넘는 완전 재현을 보장하지 않는다.[6]

고정·기록할 항목: 환경·평가기 버전, 컨테이너 digest, DB/문서/코드 hash, 모델 버전, 프롬프트와 실행 프레임워크, 샘플링 설정, 전체 도구 입출력, 의미화된 상호작용, 권한 변경, 외생 이벤트 원장, 비용 원장, 최종 산출물 hash, 시스템 장애와 재시도 사유.

금액·카운트·논리 상태는 가능하면 정수/고정소수점과 정규화된 직렬화로 재생한다. 실수 연산이 필요하면 수치 허용오차와 지원 실행환경을 미리 명시한다. 같은 기록을 다른 기기에서 재생했을 때 상태 차이가 발생하면 환경 결함으로 조사한다.

## 5. 성과의 인과적 귀속

### 5.1 비교 대상

π_0는 기업이 멈춘 세계가 아니라 FDE가 추가 투입되지 않은 기존 운영 정책이다. 기존 인력과 기존 시스템은 계속 일한다.

같은 초기 상태에서 다음 세계를 분기한다.

- 기존 운영 정책 π_0.
- 평가할 AI 시스템 π_A.
- 인간 FDE 또는 AI 도구를 사용하는 인간 FDE π_H.

비교 세계에는 같은 외생 수요·지연·고장 충격을 제공한다. 정책에 의해 발생한 주문, 장애, 채택 등의 결과까지 강제로 동일하게 맞추지는 않는다.

상태전이를 S[t+1] = F_j(S[t], a[t], ξ[t])로 표현할 때 공유하는 것은 외생 잡음 ξ이고, 정책에 의해 바뀐 상태와 행동은 각 세계에서 다르게 전개된다. 난수는 순차 호출 횟수보다 사건 종류·개체·시점에 연결하여 불필요한 행동으로 향후 난수를 밀어내지 못하게 한다. 공통 난수는 분산 감소를 위한 고전적 방법이며, 실제로 분산이 줄었는지는 점검한다.[7]

새로운 외생 조건에서 정책을 평가할 때는 에이전트를 처음부터 다시 실행한다. 과거 행동 기록을 새 세계에 기계적으로 재생한 결과를 ‘새 상황 적응 능력’으로 보고하지 않는다.

### 5.2 개입 순가치

실행 r의 짝지은 순효과:

G_jr(A) = [U_j(π_A; ξ_r, η_r) - U_j(π_0; ξ_r)] - [C_j(π_A; ξ_r, η_r) - C_j(π_0; ξ_r)]

여기서 η는 에이전트 실행 변동이다. Δ_j(A) = E[G_jr(A)]가 프로젝트 분포에서의 기대 개입 순효과다. U와 C는 각각 같은 개입·사후 운영 기간을 대상으로 하며 비용 항목은 한 번만 차감한다. 돈으로 정당하게 환산할 수 없는 안전·권한 문제는 이 식의 가중치가 아니라 별도 제약으로 둔다.

예시(실측이 아닌 설명용 수치): 이전 순운영가치 1,000만원, AI 투입 후 1,400만원, 같은 외부 호황에서 미투입 세계 1,300만원, 추가 개입비 40만원이라면 순기여는 60만원이다. 단순 전후 증가액 400만원이 아니다.

이 인과효과는 시뮬레이터 가정 아래의 효과다. 현실에서 같은 크기의 효과가 난다는 주장은 현장 검증을 필요로 한다.

## 6. 점수 체계

### 6.1 주 결과: 순효과와 전체 프로젝트 성공률

프로젝트마다 고객과 독립 검토자가 사전에 정한 양의 의미 있는 가치 단위 m_j로 정규화한다.

I_j(A) = Δ_j(A) / m_j, m_j > 0.

m_j는 모델 결과를 본 뒤 선택하지 않는다. 원 단위 성과와 가정 민감도를 함께 공개한다. I는 확률이 아니며 음수와 1 초과 값을 허용한다. 악화를 0으로 잘라 숨기지 않는다. 인간 평균이나 전지적 최적 해를 분모에 두지 않는다.

하위 집계는 반복 → 변형 → 독립 사례군 → 도메인 순서로 평균낸다. 도메인과 독립 사례군에 사전 지정한 동일 가중을 주는 것을 코어 기본값으로 한다. 실제 산업 비중 가중치는 별도 적용 점수로 보고한다. 템플릿 변형을 많이 만든 도메인이 자동으로 높은 비중을 차지하지 않게 한다.

전체 프로젝트 성공은 해당 사례의 실행 가능한 인수 계약 충족 여부다. 개선이 필요한 사례에서는 순기여, 품질, 승인된 운영 적용, 지속 사용, 인수·복구 검사 등을 모두 충족해야 한다. 정당한 무개입 사례에는 새 배포·사용률 조건을 강제하지 않고, 증거로 지지되는 중단/유지 판단과 상태 보존·모니터링·인계 조건을 사용한다. 무개입 사례 비중과 성공률은 별도로 공개한다. 예상 밖의 유효한 해결책은 정답 목록에 없다는 이유로 탈락시키지 않는다.

### 6.2 채택·유지

적용 대상 업무 기회 중 새 방식으로 수행되고 독립 품질 검사를 통과한 업무의 비율을 사용한다. 클릭 수, 로그인 수, 당사자의 호감 표현은 주 지표가 아니다. 분모 정의는 에이전트가 유리하게 축소하지 못하도록 독립 평가기가 고정한다. 적용 가능한 업무가 없는 상황의 0/0 처리도 사례 계약에 정의한다.

인계 이후에는 FDE의 추가 수정·감독을 중단하되 배포된 서비스는 계속 작동시킨다. 납품 시스템에 포함된 모델 호출·자동화는 허용하되 선언된 권한과 예산 안에서 비용을 계속 집계한다. 서비스 재시작, 입력 분포 변화, 담당자 변경 등의 보류 시험에서 성과 유지와 복구를 검증한다. 시뮬레이션 30일을 실제 사람이 30일 수행하는 직무 전체와 동일시하지 않는다.

### 6.3 자율성

질문 수/결정 수 비율은 쓰지 않는다. 결정 단위를 임의로 쪼갤 수 있고, 필요한 승인과 고객 조율을 잘못 벌주기 때문이다.

구분해서 기록한다:

- 환경 내 정상적인 협업: 현장 지식 확인, 승인, 요구 조율. 자율성 실패는 아니지만 상대방 노동과 지연 비용은 기록한다.
- 추가 전략 구조 요청: 평가 감독자가 문제를 선정하거나 해결 순서를 알려주는 등 FDE의 일을 대신한다. 자율 트랙 실패로 기록하고 보조 트랙으로 분리한다.
- 사고 수습·외부 구조: 횟수, 실제 노동시간, 비용, 중단 여부를 기록한다.

대규모 실행을 사람에게 떠넘기면 그 사람의 노동을 비용과 위임 업무량에서 빠뜨리지 않는다. 허용되는 협업과 외부 실행 범위는 인간·AI 모두에게 같은 역할 계약을 적용한다.

### 6.4 위험과 신뢰성

중대한 권한·안전·데이터 무결성 위반은 높은 성과로 상쇄할 수 없다. 위반 실행을 분석에서 삭제하지 말고 원 성과, 위반 유형, 실패 여부를 함께 공개한다. 불법적/비인가 변경의 성과로 안전한 시스템보다 높은 종합 순위를 받지 못하게 한다.

반복 성공의 신뢰성은 pass^k를 보조 지표로 보고한다. 같은 사례에서 독립 실행 n회 중 c회 성공했다면 추정치는 choose(c,k)/choose(n,k)다(n≥k, c<k이면 0). 이는 k회 중 한 번 이상 성공하는 pass@k와 다르다.[8] 환경 잡음과 에이전트 잡음 중 어떤 분포를 반복 샘플링했는지 명시한다.

### 6.5 과정 지표는 진단용

가설·증거·예측 결과, 범위 결정, 실험, 코드, 승인, 운영 로그 등 업무 산출물을 조사한다. 비공개 사고과정 제출은 요구하지 않는다. 인과 그래프의 이름 일치보다 보류된 개입 결과 예측과 실제 운영 개선을 우선한다. 문서의 수나 문체를 최종 성공으로 착각하지 않는다.

재사용 능력은 인계 산출물을 새 조직의 후속 배치에 제공했을 때 추가 시간·비용과 성과가 어떻게 바뀌는지 별도 짝지은 실험으로 측정한다. 플레이북의 글솜씨만 채점하지 않는다.

## 7. 사례 구성과 보류 평가

직무 사례 수집을 먼저 하고 다음 축을 교차한다.

- 기술 구조: 데이터 품질·통합, 업무 라우팅, 모델/규칙 품질, 운영 안정성 등.
- 조직 구조: 담당자·인계 누락, 승인 경로, 목표 충돌, 도입 부담, 소유권 등.
- 판단 상황: 여러 대안의 우선순위, 잘못된 대리지표, 제한된 예산, 개입 보류, 복합 원인.
- 도메인: 실제로 다른 업무와 인과 제약을 가진 복수 산업/업무 영역.

독립적으로 작성한 사례군과 같은 사례의 표현·수치·seed 변형을 구분한다. 개수 확대보다 사례군 다양성이 중요하다.

개발/시험 분리는 템플릿 원본, 문서 계보, 원인 구조, 조직 메커니즘 단위로 한다. 시험 시에는 새 조직, 새 메커니즘 조합, 별도 도메인, 별도 조직 모델로 나눠 전이를 보고한다. 사전학습에서 해당 산업을 전혀 보지 않았다고 주장하지 않는다. ‘보류 도메인’은 벤치마크 개발·튜닝에서 보류했다는 뜻이다.

표현만 바꾸는 시험은 형식 민감도 검사이고, 인과 구조를 바꾸는 시험은 적응력 검사다. 둘을 동일하게 취급하지 않는다. Procgen은 환경 다양성과 새로운 환경 일반화를 구분하는 선례지만, 자동 생성만으로 타당도가 확보되지는 않는다.[9]

쉬운 현실 사례도 남긴다. AI가 실패하는 사례만 골라 대표 업무 분포라고 부르지 않는다. 표적 약점 시험은 별도 스트레스 세트로 공개한다. 보류 문제의 상세 피드백은 제한하고, 폐기된 세트는 후속 재현을 위해 공개하는 등 오염과 재현의 균형을 관리한다.[10]

## 8. 통계 분석 계획

### 8.1 추정 단위

독립 사례군이 주 표본 단위이며, 같은 사례군의 변형·외생 seed·에이전트 반복은 하위 반복이다. 동일 사례 1,000회 실행을 1,000개의 독립 고객사로 세지 않는다.

평가 모델 간에는 같은 사례·외생 사건을 짝지어 비교한다. 코어 분석은 도메인을 고정 층으로 놓고 사례군을 집락 재표집하는 계층적 bootstrap을 사용한다. 변형과 반복을 포함한 재표집 방식, bootstrap 횟수, 난수 seed, 집계 가중치를 사전 등록한다. 인간 자료는 참가자 반복 측정이 있으므로 사례군과 참가자를 함께 반영하는 교차 임의효과 모형 또는 교차 집락 bootstrap을 사용한다. 소수 도메인에서 ‘모든 산업’으로의 신뢰구간은 만들지 않는다.[11]

보고 항목은 평균 순효과, 95% 구간, 전체 성공률, 도메인별 결과, 하위 성과 구간, 심각 실패율, 반복 신뢰성, 비용·지연, 추가 인간 구조량이다. 순위만 보고하지 않는다. 참조 시스템 및 핵심 비교를 사전 지정하고, 많은 탐색적 비교는 별도로 표시한다.

### 8.2 표본 수

파일럿에서 사례군 간 차이와 사례 내 변동을 추정한 뒤 계층 구조를 반영한 power simulation으로 결정한다.

독립적인 짝 비교의 설명용 근사:

n ≈ ((z_(1-α/2) + z_(1-β)) × σ_diff / δ)^2.

양측 α=.05, 검정력 .80, 사례 차이의 표준편차 .25, 구분할 최소 차이 .10을 가정하면 n≈50개의 독립 짝 비교가 필요하다. 이는 관측된 분산도 아니고 최종 권장 표본 수도 아니다. 집락 구조, 다중 비교, 도메인별 주장, 인간 참가자 차이는 별도로 반영해야 한다.

### 8.3 사고 0회의 해석

대표 분포에서 독립적으로 샘플링한 이항 평가 n회에서 사고가 0회일 때 단측 95% 정확 상한은 1 - .05^(1/n)이다.

- n=20: 약 13.91%.
- n=100: 약 2.95%.
- n=300: 약 0.994%.

같은 사례 반복의 상관이 있으면 이 단순 해석을 그대로 적용하지 않는다. 사고율 1% 미만을 주장하는 것과 20~100개의 데모에서 사고가 없었다는 것은 다르다.

### 8.4 실패·결측

시간 초과, 에이전트가 만든 서비스 장애, 유효하지 않은 도구 호출은 사전 규칙에 따라 실패/비용으로 포함한다. 실험 인프라 자체 결함은 독립 판정과 사전 재시도 규칙을 적용하고 원 기록을 남긴다. 유리한 실행만 골라 보고하지 않는다. 비열등성 분석의 결측 처리와 민감도 분석도 사전 등록한다.

## 9. 인간 비교 및 기능적 대체 주장

인간 FDE 단독, 허용된 AI 도구를 사용하는 인간 FDE, 자율 AI 시스템을 비교한다. FDE 채용·고용 적합성을 판단하는 검사가 아니라 시스템 연구용 직무 표본 검사로 운영한다.

동일 조건은 동일 권한, 업무 정보, 조직 자원, 목표와 운영 기회다. 인간과 AI의 토큰 수를 같게 하는 식의 공정성은 사용하지 않는다. 능력 트랙에서는 공통 업무 자원 한도를 사용하고 비용·실시간 지연을 함께 보고한다. 경제성 트랙에서는 실제 총비용과 납기 조건을 맞추어 성과-비용 곡선을 비교한다. 시뮬레이션 시간, 사람의 작업 시간, 모델 실행 시간은 별도 시계로 기록한다.

인간에게 공통 인터페이스 연습을 제공한다. 같은 참가자에게 같은 숨은 원인의 변형을 반복 배정하지 않는다. 숙련도·고객 배치 경험을 확인하고 배정 순서를 균형화한다. 사례 작성자는 자신의 사례에서 인간 기준선을 제공하지 않는다.

비열등성의 예시 정의:

D = E[I_AI - I_Human+AI].

사전에 정한 실무 허용 열위 ε에 대해 D의 단측 95% 신뢰하한이 -ε를 넘는지 검증한다. 신뢰수준과 ε는 결과를 보기 전에 고정한다. ε는 임의의 ‘5점’이 아니라 실제 업무가치와 위험 기준에서 정한다.

성과 비열등성만으로 충분하지 않다. 실패 위험, 채택 유지, 비용, 추가 인간 구조, 보류 도메인 결과를 함께 요구한다. 심각 실패가 늘어났다면 평균 성과 우위로 덮지 않는다. 시험한 조건에서 핵심 업무 흐름의 기능적 대체 근거라고 보고하며 전체 FDE 직업의 소멸로 번역하지 않는다. METR도 긴 작업 성능을 실제 직업 자동화와 직접 동일시하지 않는 이유를 구체적으로 설명한다.[12]

## 10. 타당도 검증 연구

타당도는 설계서에 적는 속성이 아니라 특정 점수 해석을 지지하는 누적 근거다.[13]

### 10.1 내용 타당도

복수 조직의 실제 FDE 및 고객 담당자가 익명화한 배치 사례를 수집한다. 직무 요소와 사례의 대응표를 만들고, 역할에서 중요한데 환경에 없는 항목을 명시한다. 코드·영업·운영·고객 조율 중 어떤 부분을 과대/과소대표하는지 점검한다. 8~12명의 독립 실무자와 20~30개 초기 사례는 모집 계획의 출발점일 뿐 충분성을 입증하는 수치가 아니다.

### 10.2 응답 과정과 보조 기능 오염

단순 조회·스키마 확인 등 인터페이스 교정 과제를 둔다. 도메인 지식이 아니라 API 형식 오류 때문에 실패한 정도를 분리한다. 형식의미가 같은 문장·명칭·문서 순서 변형을 쌍으로 평가한다. 재량적 개인별 힌트는 금지하되 동일한 문법 검증/수정 규칙은 제공할 수 있다.

### 10.3 인과적 난이도 조작

같은 기본 사례의 대응 버전에서 문제 범위 제공, 구현 완료 제공, 승인 확보, 기본 채택 확보 등의 조건을 각각 추가한다. 특정 부담을 제거했을 때 어느 실패가 줄어드는지 측정한다. 정보 제공 시점을 맞추고 비용 차이를 기록한다. 제거 조건이 단순히 유리한 새 환경이 된 효과와 측정 능력의 해석을 구분한다. 특정 순서의 단계별 점수가 항상 오르도록 강제하지 않는다.

### 10.4 변별·수렴과 증분 설명력

동일한 시스템들로 코딩, 검색, 상호작용, 장기 실행 기준을 함께 측정한다. 기존 점수만으로 프로젝트 성과를 어느 정도 예측하는지, 전체 흐름 지표가 보류 사례 성과 예측에 추가 기여하는지 확인한다. 상관이 낮다는 사실 하나를 독립 능력의 증거로 삼지 않는다. 소수 모델로 안정적인 요인 구조를 발견했다고 주장하지 않는다. 직무 경험이 많은 참가자의 실패 패턴도 분석하되 ‘시니어가 무조건 이겨야 한다’는 순위 조건을 만들지 않는다.

### 10.5 조직 모델 및 외부 타당도

조직의 승인·채택 메커니즘을 현실적인 범위에서 바꿨을 때 결과와 순위가 유지되는지 시험한다. 하나의 협조적인 NPC 모델에서만 높은 점수를 내면 그 모델에 대한 성능으로 범위를 좁힌다.

저위험 인간 역할극 또는 동의받은 고객 테스트 환경에서 다른 조직의 보류 사례를 평가한다. 코어 점수가 실제 완료율, 운영 유지, 감독 노동을 예측하는지 사전 예측을 등록한 후 검증한다. 실제 현장 인과효과는 가능하면 독립 팀/조직 단위 병렬 무작위 배정으로 확인한다. 같은 팀에 순서대로 시스템을 적용하면 학습·배포 잔존 효과가 생기므로 단순 교차 실험을 독립 비교로 간주하지 않는다. 실사례는 비밀정보 제거, 동의, 보상, 위험 검토와 중단 기준을 갖춘다.

## 11. 평가기와 환경 자체의 공격적 검사

출시 전에 다음 부정 대조를 실행한다.

- 같은 정책·같은 비용의 A/A 분기에서 개입 순효과가 0인지 확인한다.
- 아무 변경 없이 외부 수요만 좋아졌을 때 그 향상이 에이전트 기여로 잡히지 않는지 확인한다.
- 대시보드 수치만 바꾸거나 문서만 그럴듯하게 써서는 점수가 오르지 않는지 확인한다.
- 실제로 품질·승인·운영 성과가 동일한 대안 구현을 둘 다 인정하는지 확인한다.
- 성과 없이 권한을 우회하거나 가짜 승인 기록을 만들면 탐지되는지 확인한다.
- 실행 중 이득이 있어도 인계 후 무너지면 성과가 낮아지는지 확인한다.
- 가치 기준, 비용 단위, 품질 손실 계수를 바꿔 순위의 민감도를 보고한다.
- 단위테스트를 교란하는 변이, 숨은 상태 유출, 반복 리더보드 탐색, 임의 로그 위조를 별도 레드팀에서 검사한다.

이 검사는 설계 요구사항이며 현재 수행 완료한 검사가 아니다.

## 12. 파일럿과 확증 평가의 분리

기술·평가 파일럿의 예시 규모:

3개 다른 업무 도메인 × 도메인별 4개 독립 사례군 × 2개 변형 = 24개 인스턴스.
각 인스턴스에 3개 외생 사건 흐름 × 2회 독립 에이전트 실행 = 시스템당 144회.

이 수치는 작동 검사와 분산 추정용 제안이다. 도메인 3개, 독립 사례군 12개로 전체 FDE 대체를 주장하지 않는다. 문제 없는/개입 보류 사례와 복합 조직 사례를 미리 포함하고, 같은 내용의 표면 변형만 늘리지 않는다. 최소 비교는 기존 운영, 단순 규칙 전략, 코딩 중심 시스템, 전체 흐름 시스템이며 이후 실무 인간 기준선을 수집한다.

확증 평가는 파일럿에 쓰지 않은 독립 사례군과 별도 도메인에서 한다. 표본 수, 자원 예산, 성공 조건, 부작용 상한, 정규화 기준, 인간 비교 집단, 제외·재시도 규칙을 파일럿 분석 후 시험 결과를 보기 전에 고정한다. 연구자가 좋은 결과가 나올 때까지 평가기를 바꾸는 행위를 방지한다.

## 13. 연구 산출물과 완료 판정

필수 산출물: 직무 범위/내용 대응표, 환경 명세, 버전 고정된 실행 환경, 독립 평가기, 공개 개발 사례, 보류 평가 관리 절차, 인간 실행 프로토콜, 사전 등록 통계 계획, 비용 원장 규칙, 전체 실행 추적, 사례별 성과 및 실패 분석, 타당도 검증 결과.

설계 문서 완성과 검증된 벤치마크 완성을 구분한다. 코어 환경이 높은 반복 재현성을 보여도 인간 조직에 대한 예측력이 없으면 주장을 ‘통제된 고객 프로젝트 시뮬레이션 수행 능력’으로 제한해야 한다. 반대로 실제 고객 성과는 좋지만 통제 재현성이 낮다면 현장 실험으로 가치가 있으나 코어 리더보드와 합치지 않는다.
