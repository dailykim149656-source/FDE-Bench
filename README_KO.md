# FDE-Bench

목표는 **AI 발전에 따른 모델·에이전트·하네스의 FDE 수행 성능, 재귀개선 가능성, 실제 FDE 업무 대체 가능성을 검증하는 실행형 벤치마크**를 만드는 것이다. 출발 질문은 “낯선 고객 환경에서 문제를 정의하고, 해결·배포·인계까지 수행하는 FDE 업무를 AI가 대체할 수 있다면 AGI의 어떤 증거가 되는가?”다. R0 산술 검사와 첫 환경 검증은 중간 단계이며 인간 비교·현장 전이는 장기 목표에 포함한다.

FDE를 본질적으로 인간만 할 수 있는 업무라고 전제하지 않고 대체 가능성을 시험한다. 또한 FDE 한 사례의 성공을 AGI 판정으로 삼지 않는다. 성과의 깊이와 수행 범위의 넓이를 구분하는 [Levels of AGI](https://arxiv.org/abs/2311.02462v5)를 참고해, 새로운 조직·문제에 대한 일반화와 자율성까지 근거를 쌓는다. FDE 대체를 AGI의 충분조건으로 보지 않는 것은 이 벤치마크의 해석 원칙이다.

현재 **실행 엔진·시스템 비교·개선 루프가 있는 합성 개발용 벤치마크**다. Python 에이전트와 실제 Codex 모델을 같은 action 프로토콜로 실행한다. SQLite 거래 처리, 승인에 묶인 배포, 개발/평가 workload 분리, 세대별 소스 보존, 고정 개선자 대조를 구현했다. **저작한 합성 메커니즘 3개(라우팅·재고·외부 작업 복구), 실제 인터뷰 0건, 선정 프로젝트 0건, 독립 실제 FDE 사례군 0개**다.

실행 세계는 `fdebench.execution-ontology.v0.1`로 명시한다. 현장 intake는 `fdebench.field-ontology.PROVISIONAL`이며 인터뷰 2–3건 전에 스키마를 잠그지 않는다. 호출 시간 초과, 프로토콜 거부, 과제 결과 오류는 서로 다른 실패 종류다. `./bench ontology`가 목록을 출력하고, `./bench ontology --artifact path.json`이 저장된 session/episode를 분류한다.

[R0 원본 복구·재현](r0_recovery.md)을 마쳤다. [인간 평가 범위 결정](human_evaluation_decision.md)의 “R1에서 연구 종료”는 사용자 의도를 잘못 해석한 문구로 정정했다. 현실 타당도 검증에는 [변경 전후 자료 접근](r1_fieldwork/outreach.md)과 최초 인터뷰 2–3건이 필요하다. 자료 확보와 별개로 현재 실행기로 시스템을 비교할 수 있으며, 그 결과를 실제 FDE 대체 증거로 확대하지 않는다. 잠정 조사 스키마는 인터뷰 전에 더 확장하지 않는다.

[새 사례 전이 실험](experiments/transfer-v1/REPORT.md)을 실제 모델로 실행했다. 세 지시문 모두 재고 품질 조건 9/9를 충족했지만, 기존 사례에서 만든 수정 지시문의 우위는 확인하지 못했다. 조건별 실행 1회의 합성 파일럿이며 실제 조직 일반화의 증거는 아니다.

[Grok 4.6 반복 실험](experiments/grok45-v1/REPORT.md) 45세션을 완료했다. 19세션이 배포·종료 및 사례 품질 조건을 충족했고, 나머지 26세션은 120초 호출 시간 초과였다. 배포된 정책에서는 품질 조건 실패가 없어, 과제 자체의 변별력보다 실행 경로의 신뢰성 문제가 드러났다.

## 실행

macOS/Linux, Python 3.12 이상과 `uv`가 필요하다. `./bench`는 잠긴 의존성을 설치하고 실행한다. 외장 ExFAT에서도 실행하도록 가상환경과 SQLite 작업 파일은 시스템 로컬 저장소를 사용하고, 완료된 데이터베이스를 결과 폴더에 저장한다. `FDEBENCH_ENV`로 가상환경 경로를 바꿀 수 있다.

```bash
./bench run --suite examples/compare.json --out runs/compare
./bench evolve --suite examples/evolve.json --generations 2 --out runs/evolve
./bench run --suite examples/codex.json --out runs/codex
```

첫 두 명령은 모델 호출 없는 **스크립트 제어군**이다. 세 번째는 로그인된 Codex CLI로 실제 모델을 호출하며 계정 사용량을 쓴다. `configured-default`는 공급자 별칭이므로 고정된 모델 스냅샷의 증거가 아니다. 모델 비교에는 suite의 `model`을 명시하고 같은 소스·하네스·자원 조건을 유지한다. [실행 계약과 결과 읽기](examples/README.md)에 시스템 설정과 명령을 설명한다.

결과에는 실행 소스, 다시 실행할 수 있는 `suite.json`, 거래 SQLite 파일, action 기록, 원 단위 지표, baseline 대비 차이, 버전과 해시가 남는다. 기존 출력 폴더는 덮어쓰지 않는다. 실행 중 코드가 바뀌면 최종 결과 발행을 거부한다. `run`은 성능 평가, `evolve`는 실제 후보 생성과 평가, `compare`는 호환되는 과거 결과 분석이다. [보존된 실행 증거](validation/README.md)에서 제어군 결과를 확인할 수 있다.

실제 회사 자료로 검증한 baseline twin은 아직 없다. [조사 도구](r1_fieldwork/README.md)는 별도로 유지한다.

```bash
python3 r1_fieldwork/select_case.py
python3 r1_fieldwork/self_check.py
```

조사 도구는 Python 3.12 이상, 표준 라이브러리만 사용한다. 첫 명령은 자료의 검토 준비 상태를 출력한다. 두 번째는 임시 합성 입력으로 선택기의 오판 방지 동작을 검사한다. 테스트 통과는 실제 사례나 twin fidelity 검증을 뜻하지 않는다. 새 실행 엔진의 런타임 의존성은 Pydantic이며 `uv.lock`으로 버전을 기록한다.

| 주장 수준 | 벤치마크에서의 의미 |
|---|---|
| R0 | **원 참조 검사 재현 확인.** 제공된 ZIP의 원 코드를 보존·버전 관리하고 `--seeds 1000`으로 20/20 통과 및 §13 수치를 확인했다. 합성 산술·불변성 검사 범위이며 모든 검사가 1,000 seed를 쓰는 것은 아니다. [결과·버전·범위](r0_reference/reproduction.json)를 함께 인용한다. |
| R1 | 검증한 통제 프로젝트 범위에서 시스템의 실제 수행 성과·개선 효과를 보고한다. 환경 구현·검증만으로 성능 결과를 얻은 것은 아니다. 재귀개선 결과도 시험한 조건의 범위에 한정한다. |
| R2 | 장기 목표인 인간 FDE 기준 집단과의 비교. 별도 프로토콜의 비동기 다일 수행으로 설계하며 4시간 견적을 사용하지 않는다. 모델 간 비교는 그 전에 시작할 수 있다. |
| R3 | 장기 목표인 실제 FDE 업무의 기능적 대체 근거. 조직 전이·신뢰성·경제성·추가 인간 구조 노동·인계의 검증이 필요하다. R3 충족도 AGI 전반의 판정으로 자동 승격하지 않는다. |

## 이 벤치마크가 답할 세 질문

| 질문 | 필요한 비교 | 부족한 근거를 대신할 수 없는 것 |
|---|---|---|
| AI 발전으로 무엇이 좋아졌는가? | 모델·에이전트·하네스를 각각 고정하거나 바꾼 대조와 실제 시스템 전체 조합의 비교 | 여러 요소를 동시에 바꾼 총점 차이를 모델 자체의 발전으로 부르는 것 |
| 시스템이 자신을 개선할 수 있는가? | 세대별 수정 계보와 개선 절차, 고정된 조상 대조군, 동등한 탐색 예산, 보류 사례의 성능·비용 | 메모리 축적, 외부 모델 교체, 최종 시험 점수에 맞춘 반복 수정만으로 재귀개선을 주장하는 것 |
| 실제 FDE 업무를 대체하는가? | 프로젝트 전체의 인간+허용 AI 도구 기준선, 새로운 조직·문제, 정상 협업과 추가 구조 노동, 운영·인계 결과 | 단일 시뮬레이션의 높은 점수나 합성 산술 검사 통과 |

여기서 모델은 추론 모델의 스냅샷, 에이전트는 프롬프트·계획·메모리·도구 사용 정책, 하네스는 실행·컨텍스트·도구 연결·재시도 등의 런타임으로 구분한다. 실제 구현에서 둘을 분리할 수 없으면 결합된 시스템 비교로 표시한다. 평가 환경·숨은 시험 자료·채점기는 비교 중 고정하며 개선 대상의 쓰기 영역에 넣지 않는다. `model_snapshot`, `agent_revision`, `harness_revision`을 `evaluator_version`과 별도로 식별해야 한다. 이는 향후 실행 기록의 요구사항이며 현재 intake 스키마를 확장한 것이 아니다.

모델만 바꾼 비교는 해당 에이전트·하네스에서의 효과이고, 하네스만 바꾼 비교도 해당 모델에서의 효과다. 가능한 교차 조합으로 상호작용을 확인하고 호환되지 않는 조합은 결과가 없는 것으로 표시한다. 시간이 지난 시스템의 진척 비교에도 같은 평가 조건을 적용한다. 평가 버전이 바뀌면 v0.2 §11.3의 연결 실행을 요구하며, 과거 모델을 재실행할 수 없으면 직접 향상량을 확정하지 않는다.

## 재귀개선 검증의 최소 구분

v0.2의 Cold / Continual은 실행 상태·경험 재사용 규칙이다. 재귀개선의 증거가 자동으로 되지는 않는다. 자기 코드 수정과 벤치마크 평가를 결합한 [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954v3)은 방법의 선례이며 FDE 전이의 검증은 아니다. 이 벤치마크에는 다음 구분이 추가로 필요하다.

- 개선에 쓸 개발·검증 사례와 최종 보류 사례를 계보 단위로 분리한다. 최종 시험 점수·궤적은 수정이나 승격 결정에 제공하지 않는다. 개선 계보를 고정한 뒤 각 세대를 보류 자료에서 평가한다.
- 원형 시스템 S0, 개선된 S1, 다음 세대 S2의 스냅샷과 수정 diff를 남긴다. 각 수정을 누가 만들었는지, 실제 다음 개선을 어느 세대가 수행했는지, 외부 모델·사람이 무엇을 도왔는지 기록한다. 부모 선택·승격 규칙과 탈락한 후보도 남긴다.
- 첫 실험은 기반 모델을 고정해 에이전트·하네스 개선을 구분한다. 모델 가중치 갱신이나 공급자 교체가 있으면 별도 조건이다. 고정 조상, 같은 예산으로 추가 탐색하는 고정 개선 절차와 비교해 단순 추가 시도 효과를 확인한다. 새 세대가 더 좋은 후속 개선을 만드는지도 별도 비교한다.
- 각 세대를 같은 배포 자원 조건에서 평가하고, 전체 개선 과정의 호출·시간·실패 후보·인간 지원 비용도 기록한다. 성능 향상과 경제성 향상을 분리한다. 원래 수행의 회귀·실패와 다른 사례로의 전이를 함께 보고한다.
- 새 세대의 성능 향상은 자기개선의 근거가 될 수 있다. 개선된 세대가 다음 개선을 수행하고 그 이득이 보류 사례에서도 유지되는 것은 시험한 루프의 재귀개선 근거다. 유한한 실행으로 무제한 개선이나 AGI 도달을 입증했다고 하지 않는다.

현재 `evolve`는 두 계보를 만든다. recursive 계보에서는 수정된 세대가 다음 개선을 수행하고, fixed_optimizer 계보에서는 원래 개선자가 현재 후보를 계속 수정한다. 양쪽의 호출 제한·세대 상한은 같다. 모든 계보를 `lineage.freeze.json`으로 고정한 뒤 평가하며, 최종 시험 점수는 개선 입력에 넣지 않는다. 실패 후보와 수정 제안 비용도 남긴다. 예제는 예정된 코드 변경을 수행하는 제어군이므로 `improvement_evidence=scripted_control_mechanics`다. 독립 보류 사례가 없고 공개 생성기를 쓰므로 전이·시험 비밀성·AI 재귀개선이 입증된 것은 아니다.

## 첫 벤치마크 사용판의 완료 조건

실행 패키지는 아래 기계적 경로를 제공한다. 아래 3번의 **실제 운영 재현·개입 반응 타당도**는 아직 검증하지 못했으며, 현재 배포판의 주장은 합성 환경 내 수행에 한정한다.

1. 초기 시스템·runbook·승인 경로·허용 수정 계층을 가진 사례를 초기화하고, 동일한 도구·정보·자원 규약으로 시스템을 실행하는 공통 실행기가 있다. 고객 목표와 초기 환경을 제시하되 해결 과제·구현 정답을 미리 알려주지 않아 문제 정의 능력을 평가에 남긴다.
2. 모델의 코드·설정 변경이 실제 transaction 경로를 바꾸며 독립 품질 검사, 비용·운영자 개입, 인계 후 충격의 결과가 원장에 기록된다. 모델의 답변이나 자기평가로 점수를 대신하지 않는다.
3. baseline 재현과 허용 개입 메커니즘을 검증하고, 같은 초기 상태·외생 사건에서 기준 정책과 에이전트의 결과를 대조한다. 실패와 권한 위반도 결과에 남긴다.
4. 둘 이상의 모델·에이전트·하네스 설정을 실제 실행해 원 단위 성과, baseline 대비 차이, 반복 변동, 실패·비용을 비교한다. 무엇을 고정하고 바꿨는지 표시하며 정당한 집계 근거가 없으면 임의 총점을 만들지 않는다.
5. 다른 사용자가 실행할 수 있는 명령·환경·결과·버전을 묶고, 개발용과 평가용 workload를 구분한다. 첫 사례 1개의 결과는 그 사례 범위로 보고하며 일반적인 FDE 능력 순위로 확대하지 않는다.

이후 독립 사례군과 검증 범위를 늘려 재귀개선·인간 비교·현장 전이까지 벤치마크의 질문을 넓힌다. R0–R3는 주장의 근거 수준이며 제품 개발의 종료 조건이 아니다. 인터뷰는 현재 선택한 현실 자료 기반 사례를 만드는 수단이고 최종 산출물은 실행·평가 패키지다.

기본 라우팅 사례의 수정 계층은 라우팅 규칙·기본 큐·중복 억제 설정이다. 새 `transfer` 재고 사례에서는 이벤트 순서·중복 억제·쓰기 방식·상태 보존을 설정하며 구간 사이 재고 상태를 이어받는다. 자유로운 고객 코드베이스 개발이나 조직 설득 전체를 측정하지 않는다. 라우팅 인계 검사는 에이전트 접근을 끝내고 배포 설정을 고정한 뒤, **상태가 초기화된 별도 거래량·문구 변화 구간**을 실행한다. 구간 사이 backlog·계정 상태의 연속성은 아직 구현하지 않았다. 운영자 시간은 사전 정의한 시뮬레이션 비용이며 실제 인간 노동 측정이 아니다. 에이전트 프로세스는 협력적인 로컬 실행이며 악성 코드 격리 샌드박스가 아니다.

첫 사례에서는 유익한 개입이 가능한 좁은 B2B 운영 시스템을 다룬다. 무개입 판단 사례는 아직 구현하지 않았다. 두 번째 재고 사례도 유익한 개입이 가능한 전이 검사다. 한 팀이 R1 작동 검사를 진행할 수 있지만 일반적인 능력 순위를 주장하려면 독립 저작팀 검증과 조직·사례 다양성의 근거가 추가로 필요하다.

다음 자료는 **실제 runbook + 개입 전 관측자료 + replay 가능한 workload + 실제 변경의 적용 대상·시점·버전 및 전환 중/후 결과를 연결한 기록**이다. 과거 개입 하나의 기록도 인과 식별의 충분조건은 아니므로 동시 변경·외부 충격·비교 구간을 함께 확인한다. [사례 검토표](r1_fieldwork/case_review.md)에 baseline 검증과 개입 범위 검증을 나눠 기록한다.

intake의 `schema_version=2`는 **잠정(PROVISIONAL)** 형식이다. 실무 사례가 이 구조에 맞지 않으면 원래 설명을 보존하고 형식을 고친다. [산출물 명칭 감사](r1_fieldwork/improvement_report.md)의 기준은 “이름이 실제 확인한 근거보다 더 주장하지 않는가”다.

v0.1과 Downloads의 v0.2 원본은 보존했다. 복구한 v0.2 배포 파일 5개는 `r0_reference/original/`에 그대로 보존한다. archive의 v0.2에는 R0 재현 확인·인간 시간 가정 정정 주석을 붙였으며 새 연구 프로토콜 버전은 만들지 않는다.
